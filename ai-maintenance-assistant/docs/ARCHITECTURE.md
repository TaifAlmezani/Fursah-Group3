# وصف المشروع بعد الإصلاح

## المكونات

| الجزء | التنفيذ الفعلي |
|---|---|
| الواجهة | React وVite وTypeScript، مع التحقق من ردود API بواسطة Zod |
| API | FastAPI؛ إنشاء بلاغ واستكماله وفحص الجاهزية |
| سير العمل | LangGraph مع SqliteSaver لحفظ التوقف والاستكمال |
| ASL المحلي | llama.cpp على CPU، أو Transformers عند اختيار إعداداته |
| RAG | embeddings محلية متعددة اللغات، FAISS IndexFlatIP ومتجهات مطبّعة لحساب cosine |
| البيانات | SQLite للأجهزة والتذاكر، وقاعدة منفصلة لحالة المحادثات |

## ترتيب المعالجة

1. ASL يستخرج نوع الجهاز والموقع والأعراض والخطر.
2. قواعد Python تحسب الأولوية والتحذير قبل سؤال الاستكمال.
3. نقص المعلومات يوقف المسار، مع التحذير إن وجد.
4. المطابقة تراعي الغرفة والدور والمبنى، بدون اختيار جهاز بديل من موقع آخر.
5. إذا تعددت النتائج يختار المستخدم. اختيار غير صالح لا يستأنف المسار؛ والجهاز يُراجع من القاعدة بعد الانتظار.
6. RAG يرشح إجراءات حسب نوع الجهاز والأعراض والمخاطر وحد التشابه.
7. ASL يختار معرفات إجراءات متاحة فقط. نص التوصية يأتي من المرجع، وليس إصلاحًا حرًا من النموذج.
8. تُحفظ التذكرة بحالة `created` أو `escalated`، مع نسخة المراجع والتوصية. الرد يتأكد من السجل المحفوظ.

`active` يظهر للمستخدم «بالخدمة»، و`inactive` يظهر «خارج الخدمة». لا ننشئ تذكرة لجهاز غير مسجل أو خارج الخدمة.

## API

- `POST /api/maintenance/requests`: `description` و`location` اختياري.
- `POST /api/maintenance/requests/{thread_id}/continue`: `input_type=text` مع `text`، أو `input_type=asset_selection` مع `asset_id`. كلاهما يتطلب `step_id` الذي رجع مع سؤال الاستكمال الحالي.
- `GET /api/maintenance/requests/{thread_id}`: قراءة الحالة الحالية دون استكمال أو إعادة تنفيذ. يرجع السؤال ومعرّف خطوته، أو النتيجة النهائية، مع وصف البلاغ وموقعه لاستعادة الواجهة.
- `/health`: التطبيق يستجيب؛ لا يثبت جاهزية النموذج.
- `/ready`: جاهزية قاعدة البيانات والمسار وASL والـRAG. فشل الاعتماد يرجع 503.

`thread_id` ثابت للمحادثة، و`request_id` جديد لكل استدعاء. الاستكمال بعد اكتمال البلاغ يرجع 409.

معرّف `step_id` يأتي من interrupt المحفوظ في LangGraph، ويبقى ثابتًا عند قراءة الحالة أو إعادة فتح checkpoint. بعد استهلاك الإجابة يتغير مع السؤال التالي؛ معرّف قديم يرجع 409 دون إضافة إجابة أو تشغيل المسار. إغفال المعرّف يرجع 422. الواجهة وأدوات التحقق تستخدم العقد المحدّث؛ العملاء السابقون يحتاجون إرسال هذا الحقل، ونشر الواجهة والخلفية يجب أن يشمل النسختين المتوافقتين.

يتحقق API من وصف غير فارغ بعد إزالة الفراغات وبحد 4000 محرف، وإجابة نصية غير فارغة بحد 2000 محرف، وموقع اختياري بحد 2000 محرف. يتحقق أيضًا من توافق حقول الإجابة مع `input_type` قبل تشغيل المسار.

الاستكمال يأخذ قفلًا خاصًا بالمحادثة قبل قراءة checkpoint وحتى تجهيز الرد. الطلب المتزامن لنفس المحادثة يرجع 409، بينما المحادثات المستقلة تُعالج بالتوازي. القفل مشترك بين عمليات الخادم التي تستخدم مسار checkpoint نفسه، ويتحرر تلقائيًا إذا توقفت العملية. ملفات القفل داخل `<checkpoints_db_path>.locks/` تبقى بعد الاستخدام؛ لا تُحذف أثناء تشغيل الخوادم. هذا التصميم يستخدم تخزين SQLite المحلي؛ تشغيل خوادم على أجهزة منفصلة بتخزين مستقل يحتاج قاعدة مشتركة وآلية أقفال موزعة.

إنشاء التذكرة يستخدم `operation_key = thread_id` مع فهرس UNIQUE ومعاملة SQLite. إعادة تنفيذ خطوة الحفظ بعد تعطل checkpoint تعيد رقم التذكرة المحفوظ، ولا تنشئ تذكرة ثانية. بلاغ جديد لنفس الجهاز يستخدم محادثة جديدة ويظل مسموحًا. عند ترقية قاعدة قديمة، يُحجز مفتاح لكل محادثة لها تذاكر؛ إن وجدت تذاكر مكررة قديمة تبقى محفوظة للمراجعة، ولا يحذفها الترحيل.

داخل معاملة حفظ التذكرة يعاد التحقق من نوع الأصل وحالته والغرفة والدور والمبنى مقابل النسخة التي طابقتها خطوات المسار. تغيير الموقع أثناء الاستدلال يوقف الحفظ بدل إصدار تذكرة بموقع قديم. بعد التزام التذكرة تبقى بيانات البلاغ التاريخية محفوظة عند قراءتها لاحقًا.

أخطاء الحصول على المسار وقراءة حالته وتشغيله وتجهيز الرد ترجع استجابة منظمة تحتوي `error_code` و`request_id` و`thread_id`، وتُسجل التفاصيل داخليًا. أخطاء التحقق المقصودة تحتفظ برموز 404 و409 و422.

## سياسة عرض تحذيرات المخاطر

تعرض `evaluate_safety` جميع التحذيرات المعروفة مرة واحدة بترتيب عرض ثابت: `fire_or_smoke` ثم `electrical_risk` ثم `exposed_wires` ثم `flooding`. لا يعتمد ترتيب العرض على ترتيب استخراج النموذج. النص الناتج يبقى سلسلة واحدة في `safety_message` باستخدام نصوص `SAFETY_MESSAGES` الحالية، ويرجع `None` عند غياب مخاطر معروفة. الإشارات غير المعروفة لا تولد نصًا جديدًا.

ترتيب العرض منفصل عن حساب الأولوية والتصعيد، ولا يمثل ترتيبًا لتنفيذ إجراءات ميدانية. أثناء الاستكمال يحتفظ المسار بالمخاطر السابقة ويضيف المكتشفة حديثًا ثم يعيد تكوين التحذير. نص التحذير النهائي يُحفظ في التذكرة نفسها ويظهر في الرد. التذاكر القديمة لا يعاد توليد تحذيراتها. تغيير صياغة تعليمات السلامة أو اعتمادها ميدانيًا عمل مستقل عن تثبيت ترتيب عرض النصوص الحالية.

## حدود واضحة

في الوضع الفعلي تحتفظ الواجهة بمعرّف المحادثة فقط في `sessionStorage` بمفتاح ذي إصدار، وتقرأ الحالة من API عند تحديث الصفحة. لا تعيد POST للاستعادة. إذا كانت المحادثة منشغلة تعيد GET حتى تتاح القراءة أو تنتهي مهلة الطلب. بدء بلاغ جديد يمسح المعرف المحفوظ. الوضع mock محاكاة مؤقتة داخل الصفحة ولا يحفظ جلسة عبر reload.

تعرض بطاقة النجاح تحذير السلامة إذا أرسله API، حتى عندما لا تكون الحالة حرجة. يتحقق عقد الرد في الواجهة من اتساق success/created وcritical/escalated والأولوية، ويشترط تحذيرًا غير فارغ للحالة الحرجة. بيانات الأجهزة الطويلة تلتف داخل البطاقات.

المحلل heuristic المعلن للتجربة يفحص إشارات المخاطر بصورة مستقلة ويتعامل مع صيغ نفي محلية مختبرة، ولا يفترض not_working عندما لا يذكر المستخدم عرضًا. يظل محلل كلمات محدودًا ولا يثبت فهم كل صيغ العربية؛ تشغيل النموذج العصبي والتحقق منه مسار مستقل.

المعرفة الحالية ستة إجراءات من ملفات المشروع. ما تغطي كل الأعطال أو مخاطر الحريق؛ الحالات بدون إجراء مناسب تتحول للفحص الميداني. التوصيات تُعرض كمراجع المشروع بدون ادعاء اعتماد الشركة المصنعة.

أزمنة trace مقاسة بـperf_counter لكل خطوة مكتملة. لا تشمل انتظار المستخدم أو كامل زمن HTTP أو كل كتابة checkpoint. ما نعرض وقتًا مختلقًا لخطوة فشلت أو توقفت قبل اكتمالها.

التذاكر القديمة لا تتغير؛ أعمدة التوصية الجديدة تبدأ لها بقيمة `legacy` ومراجع فارغة. تعديل المعرفة يستلزم إعادة بناء فهرس RAG.
