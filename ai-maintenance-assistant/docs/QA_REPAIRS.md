# إصلاح ملاحظات QA

يُحفظ تقرير الاكتشاف الأصلي في `QA_AUDIT.md` وأدلته في `qa/observations.json`. هذا المستند يصف التنفيذ اللاحق في مساعد الصيانة فقط.

| الملاحظة | الإصلاح |
|---|---|
| QA-01: تحذير غير مصعّد لا يظهر | بطاقة النجاح تعرض `safety_message` كتنبيه عند وجوده، مع إبقاء قواعد الأولوية والتصعيد |
| QA-02: تذكرة بموقع قديم بعد نقل الأصل | مقارنة الغرفة والدور والمبنى والنوع والحالة داخل معاملة SQLite قبل إدراج التذكرة؛ تغير البيانات يوقف الحفظ |
| QA-03: إجابة قديمة تدخل في خطوة جديدة | إرجاع معرّف interrupt الحالي باسم `step_id`، واشتراطه في الاستكمال والتحقق منه تحت قفل المحادثة |
| QA-04: تجاوز حدود الإدخال | تحقق Pydantic بعد trim: وصف 1–4000 محرف، وإجابة 1–2000 محرف، وموقع اختياري بحد 2000؛ حقول الإجابة توافق نوعها |
| QA-05: ردود متناقضة أو تحذير حرج فارغ | تحقق Zod من created/success وescalated/critical والأولوية والتحذير غير الفارغ قبل العرض |
| QA-06: فقد الاستكمال بعد reload | حفظ معرّف المحادثة فقط داخل جلسة المتصفح، وGET لاستعادة السؤال أو الاختيار أو النتيجة؛ الاستعادة لا تعيد إرسال POST |
| QA-07: قص metadata الطويلة | السماح بالتفاف الكلمات الطويلة داخل بطاقة الجهاز، وتقييد العرض مع الحفاظ على دائرة الاختيار والتركيز |
| QA-08: إغفال مخاطر ونفي في heuristic | فحص المخاطر بصورة مستقلة، واستبعاد صيغ النفي القريبة المختبرة، وإزالة العرض الافتراضي المختلق، ودعم صيغ فعل مؤنثة |

## تحديث عقد الاستكمال

يرجع السؤال الحالي `step_id`. إرسال الإجابة يحتاج المعرف نفسه:

```json
{"input_type":"text","text":"B12","step_id":"<step_id from current response>"}
```

معرّف مفقود يرجع 422، ومعرّف مستهلك أو يخص خطوة سابقة يرجع 409. النص نفسه يمكن استخدامه في خطوتين مختلفتين إذا أُرسل مع معرف كل خطوة؛ لا يوجد حذف بناء على تطابق نص الإجابة.

تحتاج العملاء السابقة إلى تحديث العقد. الواجهة وmock وأدوات المشروع واختباراته حُدّثت؛ يجب نشر الواجهة والخلفية المتوافقتين معًا. يمكن قراءة السؤال الحالي ومعرفه دون تنفيذ المسار عبر `GET /api/maintenance/requests/{thread_id}`.

## الاستعادة وحدودها

الواجهة الفعلية تخزن معرف البلاغ فقط، لا نسخة من التذكرة أو المحادثة، ثم تستعيد الحقيقة من الخادم. يبقى السؤال ومعرف الخطوة بعد إعادة فتح checkpoint، ويظهر الاكتمال الذي حدث من تبويب آخر. إذا كان الخادم يعالج الاستكمال، تعيد الواجهة GET ضمن مهلة القراءة. بعد فقد رد استكمال محفوظ يمكن تحديث الصفحة لاسترجاع النتيجة دون تذكرة إضافية.

بدء بلاغ جديد يمسح المعرف. تعطيل تخزين المتصفح لا يعطل العمل في الصفحة الحالية، لكنه يمنع الاستعادة بعد reload. وضع mock يبقى عرضًا مؤقتًا داخل الصفحة. رد الإنشاء الأول إذا ضاع قبل وصول معرف المحادثة يبقى نتيجة غير مؤكدة؛ لا يُعاد إنشاء الطلب تلقائيًا.

## التحقق

- نجح الفحص الكامل للخلفية بـ154 اختبارًا، منها حالات QA السابقة واختبارات الاستعادة والنفي الجديدة.
- نجح الفحص الكامل للمتصفح بـ42 اختبارًا، بما فيها الحالات الـ13 في مجموعة QA والاستعادة بعد فقد الرد وانشغال القراءة.
- نجحت خمسة سيناريوهات للمسار الكامل باستخدام ASL العصبي المحلي وembeddings حقيقية وقواعد وفهارس مؤقتة. تشمل المخاطر المركبة والنفي وسؤال الاستكمال واختيار الجهاز وإرسال معرّف الخطوة والأرقام العربية.
- بناء الواجهة ناجح، وفحص التنسيق لا يُظهر أخطاء.

الملخص الآلي ونتائج الحالات وبصمات ملفات التنفيذ بعد الإصلاح في `qa/repaired-observations.json`. تبقى `qa/observations.json` وصور تقرير التدقيق سجلًا لحالة الاكتشاف قبل الإصلاح.

أُدخلت حالات QA في مجموعات الاختبار الافتراضية. عدم مطابقة نتيجة في المستقبل يُفشل الاختبار مباشرة؛ لا توجد xfail لإخفاء إخفاق.

صيغ النفي المختبرة تعالج أمثلة التدقيق ولا تحول heuristic إلى محلل لغوي عام. لم تتغير نصوص تحذيرات السلامة الحالية ضمن هذه المعالجة، وتقييم صياغتها ميدانيًا مستقل عن اختبار العرض والحفظ.
